ISORYN-D-015 PROPOSED (WO-0002 / ADR-0002): the `editor` target carries a host-memory prerequisite that parallelism cannot relieve - upstream generates a translation unit over 100 MB (`editor/translations/doc_translations.gen.cpp`, 102,310,230 bytes at the pinned tag) that `cl.exe` fails with `C1060` at `-j8`, `-j4` and `-j1` on a 22.9 GB host - so toolchain proof on a host that cannot meet it is a completed `template_release` build plus an editor smoke case recorded as `NOT_AVAILABLE` with the exact failing command and log, never as a silent omission and never as a passed line.
ISORYN-D-016 PROPOSED (WO-0002 / 09-TOOLCHAIN-AND-BENCHMARK-BASELINE.md): a frame-time baseline is admitted only from a windowed run on a device that demonstrably draws. The gate is readback, not exit code: a path is accepted only when the same binary and workload can write golden frames under `--write-movie --fixed-fps`, because a run can complete its loop, print a full metric series and still have no verifiable output. On this host no path passes that gate - the Vulkan loader skips the current AMD ICD and the surviving device refuses every shader module (reproduced by upstream's published binary for the same tag, though that binary keeps rendering where this build segfaults about 3 s in, so the refusal is host state and the early exit is not - `windowed-output-sink-control.txt`), the OpenGL path segfaults on both artifacts before the workload is instantiated with no harness line reaching either the console capture or the engine's own log file, and `d3d12`, the only path that completes the harness here and prints a full series with non-zero submission counters and no logged error, hands back an empty picture when that series is asked for: the frames its `--write-movie` runs produced are four in all, byte-identical to each other, 1280x720 and black at every one of their 921,600 pixels, although the workload has a current `Camera3D` and the viewport clears to a non-black default, and each such run then dies at `Can't create buffer of size: 3686400, error 0x887a0005` - a buffer exactly one 1,280x720 RGBA frame - and segfaults. This host can present, and what it returns when asked for the picture contains none of it, which is the difference between an animation and a measurement. An earlier form of this decision recorded that path as having produced no frame at all; that was a counting error, because a relative `--write-movie` path is resolved against `res://` and not against the directory the engine was launched from, and the correction strengthens the rule rather than weakening it: a frame file can exist and still be evidence of nothing, so the gate is a pixel check and not a file check. A second over-reading was corrected the same way: an absent harness line was first explained as buffered stdout dying with the process, which had never been executed, and `windowed-output-sink-control.txt` settled it by writing to the console and the engine's own `--log-file` sink at once - the line arrives in both on the paths that reach `_ready()`, including upstream's binary on the windowed Vulkan path, and in neither on this build, so the absence is a statement about how far the run got. The GPU series is therefore recorded `NOT_AVAILABLE` with those executed controls, and headless or dummy-driver numbers are never relabelled as GPU evidence. Repairing the path needs either the `d3d12` driver as a build prerequisite - a third-party SDK installation that ISORYN-D-011's isolation rule keeps off the host, and which is now known not to be sufficient by itself on this machine - or a host whose display driver passes the gate; that is a reviewer decision, not an executor workaround.
